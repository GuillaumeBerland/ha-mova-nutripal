# Camera development — experimental alpha releases

## Alpha 1 — still images (historical)

Experimental still images only. No continuous stream, microphone, recording or feeding change in alpha 1. The entity is disabled by default. Do not publish or install this branch in production before testing on HA OS. No automatic runtime download during integration startup; first image request triggers the upstream hash-verified installer. Native code runs under the HA Core process user, in a subprocess; review upstream code and third-party licenses before use. Internet is required for provisioning and first-time runtime setup. The runtime is cached under `.storage/mova_nutripal_xp2p` and not included in Git. No images are persisted by the integration (temporary JPEG in a private directory, removed after capture). The last JPEG may be reused in memory for 30 s. HA's `camera.snapshot` service may save images at the requested path. A separate cloud login is made on demand, not shared with feeding commands; coexistence and token behavior require live HA validation. Requests coalesce while a capture is in progress; requests within 30 s of completion reuse the last successful image (or return no image on failure) to limit repeated camera use. Do not add a continuously refreshing dashboard card yet. Disable the entity to stop requests. The device camera switch is checked before video provisioning; the integration never turns it on. If that check fails, no video session starts.

## Prepare sources

From the repository on the OptiPlex, with the existing validated upstream checkout and lab commit marker:

```sh
python3 tools/prepare_camera.py ../homeassistant-dreamelawnmower --commit "$(cat ../video_lab/upstream_commit.txt)"
python3 -m unittest discover -s tests -v
python3 -m compileall -q custom_components
```

Review the copied source and license, then include the entire `xp2p` package in the development branch. No external binaries or account data should be committed. The static dependency walker uses committed bytes and intentionally fails on unknown import layouts. The runtime requires requests and aiohttp (already provided by HA), Linux x86_64 or aarch64, and an FFmpeg build supporting Enhanced FLV / HEVC. Ubuntu 24.04 FFmpeg 6.1.1 was verified by the original lab. HA OS support is not verified yet. First request can take longer than HA's image HTTP timeout; if a caller times out, the shared executor capture continues through cleanup. After the capture finishes, one request within 30 seconds can retrieve the cached image. Do not repeatedly retry. Check the HA logs for sanitized stage names only. A future version will separate preparation into an explicit UI step and improve snapshot caching/lifecycle.

## Alpha 2 — native HLS live playback (experimental)

The existing camera unique ID and default disabled setting are unchanged. The camera advertises `CameraEntityFeature.STREAM` and depends on HA's native `stream` integration. `stream_source()` returns a stable random loopback URL without waiting for remote authentication. When a consumer connects, a single native session is provisioned, the device camera switch is checked, and HEVC FLV is converted to Enhanced FLV tag by tag. No separate probe consumes the native stream. HA handles HLS delivery, buffering and viewer sharing; audio AAC is preserved in the relay but client audio and browser HEVC support require testing. There is no video transcoding, external server or public proxy. The relay binds only to 127.0.0.1, refuses unrelated paths and concurrent connections, and closes the native session on disconnect or disable/unload. Do not expose its URL outside HA.

Keep **Preload stream** disabled. HA may retain a source for its HLS idle timeout even after a viewer closes. A new reader after disconnection needs a new session and fresh provisioning. A long cold start can exceed HA's stream-source read timeout; retries, browser playback and long-running session stability are not yet validated. During native live playback the camera requests a still from HA's existing stream/keyframe if available; otherwise it returns no image rather than opening a second native connection. Standalone snapshots preserve the alpha.1 FFmpeg path and 30-second cache. The gate also prevents simultaneous standalone snapshots and live sessions. An in-flight native startup or blocking read may delay cleanup; no permanent recording or forced enabling of the device camera is implemented. Debug logging for `custom_components.mova_nutripal.video` reports durations of runtime preparation, authorization, XP2P startup and JPEG capture without printing media URLs or credentials.

Do not add an always-live dashboard until stable playback and the feeding coordinator have both been checked. The alpha.1 image path was validated on HA OS by the device owner; alpha.2 has offline tests only until the new build is installed. Roll back to alpha.1 if live playback causes errors, or to v0.2.2 if the camera itself interferes with feeding data.
