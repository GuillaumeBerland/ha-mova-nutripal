# Camera development — experimental alpha releases

## Alpha 1 — still images (historical)

Experimental still images only. No continuous stream, microphone, recording or feeding change in alpha 1. The entity is disabled by default. Do not publish or install this branch in production before testing on HA OS. No automatic runtime download during integration startup; first image request triggers the upstream hash-verified installer. Native code runs under the HA Core process user, in a subprocess; review upstream code and third-party licenses before use. Internet is required for provisioning and first-time runtime setup. The runtime is cached under `.storage/mova_nutripal_xp2p` and not included in Git. No images are persisted by the integration (temporary JPEG in a private directory, removed after capture). The last JPEG may be reused in memory for 30 s. HA's `camera.snapshot` service may save images at the requested path. A separate cloud login is made on demand, not shared with feeding commands; coexistence and token behavior require live HA validation. Requests coalesce while a capture is in progress; requests within 30 s of completion reuse the last successful image (or return no image on failure) to limit repeated camera use. Do not add a continuously refreshing dashboard card yet. Disable the entity to stop requests. The device camera switch is checked before video provisioning; the integration never turns it on. If that check fails, no video session starts.

## Prepare sources

From the repository on the OptiPlex, with the existing validated upstream checkout and lab commit marker:

```sh
python3 tools/prepare_camera.py ../homeassistant-dreamelawnmower --commit "$(cat ../video_lab/upstream_commit.txt)"
python3 -m unittest discover -s tests -v
python3 -m compileall -q custom_components
```

Review the copied source and license, then include the entire `xp2p` package in the development branch. No external binaries or account data should be committed. The static dependency walker uses committed bytes and intentionally fails on unknown import layouts. The runtime requires requests and aiohttp (already provided by HA), Linux x86_64 or aarch64, and an FFmpeg build supporting Enhanced FLV / HEVC. Ubuntu 24.04 FFmpeg 6.1.1 was verified by the original lab. HA OS support is not verified yet. First request can take longer than HA's image HTTP timeout; if a caller times out, the shared executor capture continues through cleanup. After the capture finishes, one request within 30 seconds can retrieve the cached image. Do not repeatedly retry. Check the HA logs for sanitized stage names only. A future version will separate preparation into an explicit UI step and improve snapshot caching/lifecycle.

## Alpha 2 — native HLS live playback (experimental)

The existing camera unique ID and default disabled setting are unchanged. The camera advertises `CameraEntityFeature.STREAM` and depends on HA's native `stream` integration. `stream_source()` returns a stable random loopback URL without waiting for remote authentication. When a consumer connects, a single native session is provisioned, the device camera switch is checked, and HEVC FLV is converted to Enhanced FLV tag by tag. No separate probe consumes the native stream. HA handles HLS delivery, buffering and viewer sharing; audio AAC is preserved in the relay but client audio and browser HEVC support require testing. There is no video transcoding, external server or public proxy. The relay binds only to 127.0.0.1, refuses unrelated paths and concurrent connections, and closes the native session on disconnect or disable/unload. Do not expose its URL outside HA.

Keep **Preload stream** disabled. HA may retain a source for its HLS idle timeout even after a viewer closes. A new reader after disconnection needs a new session and fresh provisioning. A long cold start can exceed HA's stream-source read timeout; retries, browser playback and long-running session stability are not yet validated. During native live playback the camera requests a still from HA's existing stream/keyframe if available; otherwise it returns no image rather than opening a second native connection. Standalone snapshots preserve the alpha.1 FFmpeg path and 30-second cache. The gate also prevents simultaneous standalone snapshots and live sessions. An in-flight native startup or blocking read may delay cleanup; no permanent recording or forced enabling of the device camera is implemented. Debug logging for `custom_components.mova_nutripal.video` reports durations of runtime preparation, authorization, XP2P startup and JPEG capture without printing media URLs or credentials.

Do not add an always-live dashboard until stable playback and the feeding coordinator have both been checked. The alpha.1 image path was validated on HA OS by the device owner; alpha.2 has offline tests only until the new build is installed. Roll back to alpha.1 if live playback causes errors, or to v0.2.2 if the camera itself interferes with feeding data.

## Alpha 3 — compatibility and shared backoff

Default H.264 compatibility mode uses FFmpeg/libx264 on demand, 2 encoder threads, 30-frame GOP, AAC passthrough and rebased timestamps. H.265 native is available in integration options. Existing still capture remains unchanged. A live reader reserves its slot and waits up to 12 seconds for an already-running JPEG capture; further captures cannot take the gate. Native/provisioning errors trigger a shared 60-second video-only cooldown. HA can still retry the local URL during cooldown, but no new cloud request is made. An ordinary client disconnect does not trigger a cooldown. No changes to the feeding coordinator or feeding commands. Real HA OS encoding and HLS playback require testing. HD/SD selection is not implemented: both requested qualities produced 720x1280 HEVC in the lab. Keep preload off; disable the camera and restart or roll back if feeding updates fail.

## Alpha 4 — on-demand startup optimization

Each camera entity owns an in-memory authorization cache (no persisted tokens or tickets). A fresh authorization is reused for at most 60 seconds and never beyond the reported absolute `expireAt` minus five seconds. Unknown, relative, invalid or expired timestamps disable reuse. The Tencent P2P ticket's independent lifetime is not documented, so reuse is experimental. Login/discovery and the actual device camera-switch read still run for each session, including cache hits. Cache entries are scoped to device/model/account, invalidated on disable/unload and video failures; a failed native startup is not retried immediately, and the existing 60-second video cooldown remains. A new native session is still created on demand and always closed; no keepalive or background video connection is added.

A standalone still request without a fresh cached image waits 0.75 seconds before opening XP2P. If a native reader or HA stream output becomes active, use HA's keyframe instead. Successful live keyframes are also eligible for the existing 30-second image cache. If a standalone capture has already started, the existing single-reader gate and bounded wait still apply. This is a best-effort optimization; HA does not identify poster requests separately from explicit snapshots. The camera entity and feeding interfaces are unchanged. H.264 encoding and AAC passthrough are unchanged.

Debug logs split login/discovery, switch check, fresh/cached provisioning, XP2P negotiation and relay gate/startup timings without credentials or URLs. The time until a relay starts sending FLV is not the same as time until the browser displays its first frame. Compare cold and warm starts on HA OS, monitor feeding sensors, and check standalone `camera.snapshot` after the live session stops. The cache lifetime starts when the token is received, not when the viewer disconnects. A cache hit may be uncommon after a long live session.

HA Core 2026.11.2 defaults to low-latency HLS (`ll_hls: true`), six-second segments and one-second parts. If buffering remains the bottleneck, an optional administrator-only comparison can use the following `configuration.yaml` settings (merge with an existing `stream:` section and restart HA):

```yaml
stream:
  ll_hls: true
  segment_duration: 2
  part_duration: 0.5
```

This affects every HA camera, not just NutriPal, and may increase request frequency. It is not applied by the integration. Test after the baseline comparison, preferably on the LAN; revert if unstable. Keep preload disabled. No new HD/SD, audio gain, recording, or feeding behavior is introduced.

## Alpha 5 — cooperative still-capture preemption

A valid live HTTP reader reserves the existing single-session gate and signals a running standalone still capture to stop. Cancellation is checked before/after runtime preparation, cloud login, switch validation, authorization, native startup, and during JPEG reads and writes. FFmpeg is terminated promptly if its result is no longer needed. The gate is released only after the cloud/native context and JPEG process have been cleaned up. Native startup and individual blocking network calls cannot be interrupted safely; cancellation takes effect when they return. The existing gate wait limit (12 seconds) remains in effect. No overlapping native sessions, automatic retries or persistent video connections are introduced. An expected cancellation does not invalidate the authorization cache or trigger the failure cooldown. Actual failures retain the existing backoff; an explicit `xp2p_cleanup` failure blocks further video sessions for the lifetime of the relay. Restart HA if native cleanup fails. Camera switch validation is unchanged.

The camera uses the active HA stream's keyframe after cancellation when possible. The existing 0.75-second grace and 30-second image reuse window are unchanged: HA does not distinguish poster requests from explicit `camera.snapshot`, so a longer cache could silently return an old image to an automation. Audio passthrough, H.264 encoder settings, and feeding logic are unchanged. Global HLS configuration changes are not required or recommended for this release; other cameras must remain unaffected.

Compare `NutriPal live request preempts standalone snapshot`, `NutriPal snapshot cancelled; cleanup complete`, `NutriPal live gate acquired in ...` and `NutriPal live relay streaming (h264) in ...` against the alpha.4 gate wait of 8.7 seconds. The improvement depends on which phase was in progress when the live request arrived. Measure browser startup separately, and retest standalone snapshots and feeding sensor availability. Do not assume a fixed startup time until real HA OS tests are complete.

## Alpha 6 — passive posters and relay handoff

HA Core 2026.11.2 `Stream.async_get_image()` adds an HLS provider and starts the worker, even when called for a thumbnail during shutdown. NutriPal no longer calls that method. During an active relay, it reads HA's existing `_keyframe_converter.async_get_image()` without waiting for a new keyframe or starting another worker. This is an internal HA interface, not a stable integration API. Missing/changed converters or conversion failures fall back to a cached JPEG (or no image), never to a method that starts HLS. A pending HLS provider without an active relay also uses the cache only. The 30-second standalone image cache is retained; repeated identical live JPEG results do not extend its freshness window. A cache miss outside live playback can still request a standalone snapshot. HA cannot distinguish an automatic poster request from an explicit snapshot, so this is not a guarantee of zero camera activity from other dashboards or clients.

A second valid loopback GET arriving during the previous relay's teardown waits up to one second for the previous reader to release the gate. The old reader is never cancelled just to admit a new reader. A genuine overlapping reader is still rejected with 503 after the bounded wait. Disable, shutdown, backoff and cleanup failure remain authoritative, including for waiting readers. Normal handoff does not invalidate authorization or trigger backoff. The observed alpha.5 race was 24 ms between the refused request and prior cleanup; the new wait is intended to avoid HA's resulting ten-second retry delay, not to keep a native session open.

Keep HA preload disabled; HA still owns the HLS idle timeout. No global HLS changes, new dependencies, encoder/audio changes or feeding changes. Validate closing the camera and leaving the dashboard for two minutes, immediate reopening, standalone snapshots after expiry of the image cache, and feeding sensors. The passive keyframe path is tested with a mock of the verified HA interface; real HA OS behavior and future HA versions still need validation.
